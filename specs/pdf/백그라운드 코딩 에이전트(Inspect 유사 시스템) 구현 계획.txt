백그라운드 코딩 에이전트(Inspect 유사 시스템) 구현 계
획
개요 (Overview)
Ramp에서 개발한 Inspect와 같이, 개발자가 코드를 작성하고 검증하는 일을 백그라운드에서 자동으로 처리해주는 AI
코딩 에이전트 시스템을 구축하고자 합니다. 이 에이전트는 주어진 코드베이스 내에서 자율적으로 코드를 작성하고 수
정하며, 인간 개발자처럼 테스트를 실행하고 서비스의 동작을 검증함으로써 개발 사이클의 루프를 자동으로 닫아주는
(closed-loop) 것이 핵심입니다. 스타트업 제품으로 제공하거나 기업 내부 도구로 활용할 수 있으며, 어느 경우든
모든 핵심 기능을 구현해야 합니다. 이를 위해 최신 클라우드 인프라(예: Modal, Cloudflare Durable Objects 등)를
적극 활용하고, Python/TypeScript/React 등 가장 적합한 기술 스택을 조합하여 개발합니다. 아래에서는 시스템의 주
요 기능, 아키텍처 구성, 사용 기술과 구현 세부사항을 종합적으로 설명합니다.
주요 기능 요약 (Key Features)
구현할 시스템은 다음과 같은 핵심 기능들을 포함합니다:
샌드박스 개발환경: 각 세션마다 격리된 VM 기반 샌드박스를 즉시 생성하여, 실제 개발자 로컬 환경과 동일한
설정(Vite 번들러, Postgres DB, Temporal 워크플로 등 포함)을 제공합니다. 이 환경에서 에이전트는 자유롭
게 소스 코드에 접근하고 명령을 실행할 수 있습니다. 
AI 코딩 에이전트: 대형언어모델(LLM)을 활용한 코딩 에이전트가 동작합니다. 에이전트는 OpenCode와 같은
오픈 소스 에이전트 프레임워크를 기반으로 하여, 파일 읽기/편집, 터미널 명령 실행, 웹 요청, LSP(언어 서버)
연동 등 다양한 툴을 사용하며 코드 작성을 수행합니다. 
자동 코드 검증(Closed-Loop): 에이전트는 코드 수정 후 자동으로 테스트를 실행하고 로그/메트릭을 검사하
며, UI 스크린샷 비교까지 수행하여 자신이 만든 변경사항을 검증합니다. 이러한 자율 반복으로 인간
개입 없이도 코드의 정확도를 높입니다. 
백엔드 작업 지원: 백엔드 코드 변경 시에는 단위 테스트/통합테스트 실행, 모니터링 도구 활용(예: Sentry 에러
로그 조회, Datadog 메트릭 확인) 및 Feature Flag 조회(LaunchDarkly 등) 등을 통해 서버 사이드 동작을 확
인합니다. 
프론트엔드 작업 지원: 프론트엔드 변경의 경우 머리없는 브라우저 또는 VNC를 통해 애플리케이션을 구동하고
UI를 확인합니다. 전후 스크린샷을 찍어 Pull Request에 첨부하거나, React 컴포넌트 트리를 분석해 UI 변경
이 의도대로 되었는지 검증합니다. 
멀티 모델 지원: 다양한 LLM을 활용할 수 있도록 구현합니다. OpenAI GPT-4/GPT-5, Anthropic Claude 등 
최신 고성능 모델들을 플러그인 교체 수준으로 쓸 수 있게 하며, 자체 호스팅한 모델 또는 API Gateway를 통해
연결 가능하게 설계합니다. 
병렬 세션 및 에이전트 스폰: 에이전트 세션은 여러 개를 동시에 실행할 수 있어 개발자는 여러 시도를 병렬로
수행해볼 수 있습니다. 또한 에이전트 스스로 새로운 세션(하위 에이전트)을 스폰(spawn)할 수 있는 기능을 제
공하여, 하나의 큰 작업을 여러 작은 작업(예: 다른 서비스 레포지토리에서 리서치 수행, 보조 기능 구현 등)으로
나누어 멀티 에이전트 협업이 가능하도록 합니다. 
협업 모드(멀티플레이어): 한 세션에 다수의 사용자가 참여하여 함께 에이전트를 활용할 수 있습니다. 팀원들은
동일한 세션에 각자 프롬프트를 입력해 에이전트를 공동 제어하고, 발생한 코드 변경은 누가 요청했는지 기록됩
니다. 이를 통해 비개발자(기획자, 디자이너 등)도 개발자의 지도하에 AI를 활용하거나, 라이브 QA 세션에서 실
시간으로 수정 요청을 넣는 등의 협업이 가능합니다. 
다중 인터페이스 제공: 사용자의 업무 흐름에 녹아들도록, 여러 인터페이스를 지원합니다. 예를 들면: 회사 내 
Slack 봇으로 채팅하듯이 에이전트를 사용, 웹 IDE와 유사한 웹 인터페이스에서 세션 관리, Chrome 브라우저

PR 생성 및 CI 연동: 에이전트가 완료된 코드를 GitHub에 브랜치 푸시 및 Pull Request(PR) 생성까지 자동

자동으로 작성해줍니다. 
성능 및 모니터링: 에이전트 세션은 아주 빠르게 시작되고 응답해야 하므로, 이미 빌드된 이미지를 사용해 지연
을 최소화합니다. 실시간 스트리밍 출력으로 사용자 경험을 높이고, Cloudflare Agents SDK 등을 활용해 비
활성 시 리소스를 자동 절약합니다. 아울러 Sentry, Datadog 등의 모니터링을 통해 에이전트 자체의 오류
나 성능을 추적하고, 사용 통계 대시보드를 제공하여 팀 내 사용 현황(예: 주간 에이전트 사용세션 수, 병합된
PR 비율 등)을 투명하게 공유합니다.
이상의 기능들을 모두 갖춘 시스템은 개발자들에게 “같이 일하는 AI 동료”와 같은 역할을 하며, 이미 Ramp 등에서 내
부적으로 큰 성과(몇 달만에 전체 PR의 30%를 AI 에이전트가 작성)에 도달한 바 있습니다. 이제 이러한 시스템을 구축
하기 위한 구체적인 아키텍처와 기술 스택을 살펴보겠습니다.
전체 아키텍처 개요 (System Architecture)
OpenCode 기반 코딩 에이전트의 클라이언트/서버 아키텍처 예시. 백엔드 에이전트 서버는 Bun(JavaScript) 런타임
에서 동작하며 HTTP 인터페이스를 제공, 다양한 클라이언트(웹, CLI, Slack 등)에서 접속해 명령을 보낼 수 있다
. 본 시스템에서는 이러한 에이전트 서버를 각 세션별 VM 내부에서 실행하고, Cloudflare Durable Object를 이용
해 여러 클라이언트를 중계/동기화한다.
본 시스템은 3계층 구조로 구성됩니다:
Sandbox Execution Environment (모래상자 실행 환경) – 사용자의 코드 레포지토리별로 사전에 준비된 
컨테이너 이미지를 기반으로, Modal 등의 인프라를 통해 격리된 가상머신(샌드박스)을 즉각 실행합니다. 각 세
션은 이러한 VM 하나를 할당받아 실행되며, VM 내부에는 해당 레포지토리의 최신 코드와 개발 도구들이 설치
된 환경이 갖춰져 있습니다. 
AI Coding Agent + Session Orchestration (AI 코딩 에이전트 및 세션 오케스트레이션) – 각 샌드박스 VM
안에서 AI 코딩 에이전트 서버(OpenCode 기반)가 실행되어, 사용자 프롬프트를 받아 코드를 수정/생성하고
테스트까지 수행합니다. 한편, Cloudflare Durable Objects 기반의 세션 관리자가 각 에이전트 세션별로 존재
하여, 에이전트와 사용자 클라이언트 사이의 상태 관리와 실시간 스트리밍 중계를 담당합니다. Durable
Object는 에이전트의 메모리/대화내역을 영구적(persistent)으로 저장하고, 다수 클라이언트로부터의 입력을
큐잉하거나 브로드캐스트하며, 세션별 경량 DB(SQLite) 역할도 수행합니다. 
Multi-Channel Clients (다중 인터페이스 클라이언트) – 사용자는 Slack 챗봇, 웹 앱, 브라우저 확장 등 다양
한 방법으로 에이전트를 이용할 수 있습니다. 이들 클라이언트는 백엔드의 세션 관리자(Durable Object)에 연

할 레포지토리를 자동으로 판별하여 적절한 샌드박스 VM 세션을 생성합니다. 에이전트는 세션 내에서 코딩을 진행하며,
그 중간 결과와 로그를 지속적으로 스트리밍합니다. Cloudflare Durable Object는 WebSocket/HTTP 스트림을 통해
이 출력 정보를 사용자 클라이언트에 밀어내어 실시간으로 보여주며, 필요한 경우 중간 진행 상황을 Slack 메시지 등으
로 공지하도록 합니다. 모든 연산이 끝나면 에이전트는 변경된 코드를 Git에 커밋하고 원격 브랜치로 푸시하며, 별도의
신호를 통해 API 서버가 PR 생성 작업을 처리합니다. 이후 세션은 종료되거나, 사용자의 추가 프롬프트 입력으로 이어
질 수 있습니다.
각 구성 요소를 좀 더 자세히 살펴보고, 이를 구현하기 위한 기술과 방법을 설명하겠습니다.
샌드박스 실행 환경 – Modal 기반 VM 관리
“시간당 수십 개 이상의 풀리퀘스트를 생성할 정도로 빠르고 빈번하게 세션을 실행”하려면, 개발환경을 빠르게 띄울 수
있는 샌드박스 인프라가 필수입니다. 여기서는 Modal의 샌드박스/이미지 기능을 활용합니다. Modal은 AI 워크로드에
최적화된 클라우드 플랫폼으로, 컨테이너 이미지를 미리 스냅샷해 두고 필요 시 거의 즉시(near-instant) VM을 시작
할 수 있는 기술을 제공합니다. 우리의 전략은 다음과 같습니다:
레포지토리별 베이스 이미지 빌드: 지원 대상인 각 코드 레포지토리(예: 백엔드 서비스, 프론트엔드 웹앱 등)에
대해 Dockerfile 혹은 Modal 이미지 설정을 작성합니다. 이 이미지 빌드 프로세스는 30분마다 주기적으로 실
행되어, 해당 레포지토리의 최신 main(또는 기본) 브랜치 코드를 clone 한 뒤 의존성 설치, 초기 빌드, 캐시
생성 작업까지 수행합니다. 테스트 스위트를 한 번 실행해 두어 필요한 캐시/컴파일 결과를 미리 만들어 두는 것
도 권장됩니다. 빌드가 완료되면 이미지를 스냅샷으로 저장해 놓습니다. (이미지 빌드가多少 시간이 걸리더라
도 사용자 세션에는 영향을 주지 않습니다. 사용자는 항상 직전에 빌드된 이미지를 사용하므로 최신 30분 이내
상태만 반영하면 됩니다.) 
세션 시작 시 빠른 동기화: 사용자가 새 코딩 세션을 시작하면, Modal을 통해 해당 레포지토리의 마지막 빌드
이미지로 VM을 기동합니다. 이때 이미지가 30분 이내 옛날 것이므로, 시작 후 Git 동기화를 통해 최대 30분 사
이의 소스 변경분만 빠르게 pull 합니다. 이렇게 하면 항상 거의 최신 코드를 확보하면서도, 처음부터 clone/설
치하는 지연을 제거할 수 있습니다. 
GitHub 연동: 샌드박스 내에서 private 레포지토리를 clone/pull해야 하므로, GitHub App을 만들어 두고
세션 시작 시마다 새로운 설치 토큰을 발급받아 사용합니다. Git 설정은 커밋 작성자를 추후 PR을 열 사용자로
바꿀 수 있도록, commit 시점에만 user.name, user.email을 동적으로 변경합니다 (GitHub 개인 액
세스 토큰을 쓰지 않고도, 앱 토큰 + 유저 정보로 커밋을 남기는 방식). 
세션 영속성 및 재사용: 한 번 생성된 샌드박스 VM은 해당 세션 동안 유지되며, 사용자가 원하는 경우 수동 종료
전까지 여러 프롬프트에 걸쳐 상태를 보존합니다. 심지어 에이전트 작업 완료 후 세션이 종료되었다가도, 이후
후속 프롬프트를 보내면 마지막 상태 스냅샷을 복원하여 이어서 작업할 수 있게 설계합니다. (Modal의 파일시
스템 snapshot 기능을 활용하여, 에이전트가 만든 변경사항을 포함한 상태 이미지를 저장/복원합니다.) 
풀(pool) 및 프리워밍(pre-warming): 대기 시간을 최소화하기 위해, 사용자 입력이 감지되는 순간 미리 샌드
박스 예열을 시작합니다. 사용자가 프롬프트를 타이핑하기 시작하면 해당 레포지토리용 VM을 앞서 언급한 최
신 스냅샷으로 미리 기동해 놓습니다. 만약 사용자가 결국 엔터를 치지 않더라도 일정 시간 후 자원만 회수하면
되고, 반대로 입력이 완료되면 이미 VM이 준비된 상태이므로 바로 에이전트 실행을 시작할 수 있습니다. 또한
팀에서 사용 빈도가 특히 높은 레포지토리에 대해서는 항상 1~2개의 빈 VM을 풀로 가동 유지하는 최적화도 고
려합니다. (이 풀은 새로운 이미지 빌드가 나오면 교체하여, 구버전 코드베이스로 작업하는 일을 방지해야 합니
다.) 
초기 동기화와 동시 실행 최적화: 저장소가 매우 큰 경우, 세션 시작 시 Git pull도 수십 초 걸릴 수 있습니다. 그
러나 대부분의 프롬프트는 최근 30분 내 수정된 파일을 건드리지 않을 확률이 높습니다. 따라서 동기화가 완료
되기 전이라도 에이전트가 파일을 읽는 작업은 허용합니다. 우선 읽기-only 작업으로 코드를 분석하게 한 뒤, 동
기화 완료 후에야 쓰기 작업(편집/커밋)을 수행하도록 동기화 락(lock)을 겁니다. 이를 구현하려면 에이전트의

OpenCode 프레임워크의 경우 툴 실행 전후에 콜백을 넣을 수 있는 플러그인 시스템이 있어 이러한 제어가 비
교적 간단합니다. 
이미지에 최대한 모든 것 포함: VM 기동 후 설치/준비해야 할 작업을 최소화하기 위해, 도커 이미지 빌드 단계에
서 개발에 필요한 거의 모든 작업을 완료해 둡니다. 예를 들어 의존성 설치, 빌드, 테스트 실행(캐시용), 정적 자
산 컴파일 등 가능한 한 미리 수행합니다. 이미지 빌드에 시간이 오래 걸려도 상관없습니다. 빌드 완료 후 만들
어진 스냅샷 이미지를 재사용하므로, 사용자 세션에서는 이러한 준비 시간이 반복되지 않습니다.
이런 Modal 기반 샌드박스 환경 덕분에, 세션 시작 속도가 모델 응답 시간 + 알파 수준으로 빨라집니다. 사용자는 마치
로컬에서 바로 AI 도구를 쓰는 듯한 속도를 느낄 수 있고, 동시에 이 세션은 클라우드 상에서 돌아가기 때문에 사용자 로
컬 머신의 스펙과 무관하게 필요한 리소스를 활용할 수 있습니다. 또한 각 세션이 서로 격리되어 있으므로, 다수의 에이
전트 작업이 병행되어도 충돌 없고, 보안 측면에서도 세션 간 간섭이 차단됩니다.
AI 코딩 에이전트 – OpenCode 기반 구현
샌드박스 환경이 준비되면, 그 안에서 실행되는 AI 코딩 에이전트가 핵심 역할을 합니다. 에이전트는 LLM의 능력을 활
용해 코드를 생성/수정하고, 주어진 툴(tool)들을 사용하여 실제 환경을 조작합니다. 최적의 구현을 위해 Ramp의
권고대로 오픈 소스 OpenCode 프레임워크를 򟻘합니다 . OpenCode는 Claude Code 대안으로 개발된 프로젝
트로, 다음과 같은 장점이 있습니다:
서버-클라이언트 구조: OpenCode 에이전트는 HTTP 서버 형태로 동작하며, 터미널 UI나 GUI 앱 등은 그 위에
붙는 클라이언트일 뿐입니다 . 따라서 우리도 Slack 봇, 웹 UI, 브라우저 확장 등을 모두 HTTP API 클라이
언트로 구현하여 에이전트와 통신할 수 있습니다. 서버는 경량의 Bun(JavaScript 런타임) 위에서 구동되며,
고성능 HTTP 서버 프레임워크(Hono 등)를 사용해 요청을 처리합니다. 
LLM 프로바이더 유연성: OpenCode는 LLM 제공자에 구애받지 않는(provider-agnostic) 구조입니다. 설정
만 바꾸면 OpenAI, Anthropic, Google Gemini 등 다양한 모델 API를 동일한 방식으로 호출할 수 있고, 심지
어 OpenAI 호환 자체 호스팅 모델도 URL만 지정하면 붙일 수 있습니다. 이는 내부적으로 AI SDK라는 추
상화 계층을 사용해 구현되는데, 이 SDK가 각 모델 호출을 표준화해 주기 때문입니다. 이러한 구조 덕분에 향후
더 나은 모델이 나오거나 사내 전용 모델을 써야 할 때 유연하게 대처할 수 있습니다. 
풍부한 툴과 플러그인 시스템: OpenCode는 파일 읽기/쓰기, 버전관리, 셸 명령 실행, 웹요청 등 기본적인 개발
작업 툴셋을 내장하고 있습니다. 또 LSP(Language Server Protocol)와 연계해 코드를 수정하면 즉각 진
단 정보(오류, 타입򻹧 결과)를 피드백 받아 모델에게 제공할 수 있습니다. (예: 코드를 편집한 후 pyright
나 tsc 같은 LSP로부터 오류 리스트를 받아, 모델이 잘못된 코드를 인지하고 수정하도록 함.)
OpenCode는 이런 LSP 연동이나 기타 툴 호출에 대한 이벤트 버스와 글로벌 진단 맵을 가지고 있어, 에이전트
가 변경 후 발생한 오류를 맥락에 반영하도록 구현되어 있습니다. 또한 플러그인 시스템을 통해 툴 실행 전
후 커스터마이징(예: 로깅, 권한򻹧, 특정 툴 잠금 등)이 가능하므로, 앞서 언급한 Git 동기화 대기나 특정 명령
제한 등을 손쉽게 추가할 수 있습니다. 
코드 가독성과 자체 분석 가능: OpenCode 자체가 오픈 소스이므로, 에이전트(LLM)가 스스로 자신의 동작 방
식을 코드 레벨에서 읽어 이해하도록 프롬프트를 구성할 수도 있습니다. 예컨대 특정 툴의 동작이 모호하면 문
서 대신 OpenCode 구현체 코드를 읽어보게 할 수 있습니다. 이는 우리가 에이전트를 개발할 때도 디버깅에 도
움이 되고, 에이전트가 자기 자신을 잘못 추론하는(환각하는) 상황을 줄여줍니다. 
멀티에이전트와 확장: OpenCode는 본래 plan과 build라는 두 가지 기본 에이전트를 내장하여, 계획 수
립과 구현 수행 역할을 나누지만 추가로 사용자 정의 에이전트를 정의할 수도 있습니다. 또한 MCP(Model-
Compute-Protocol) 등 외부 에이전트 서버와 연동해 툴셋을 확장할 수 있는 기능도 있습니다. 이는 예를
들어 자체 호스팅한 특수 도구 서버나 데이터베이스를 툴로 연결할 때 활용 가능합니다.
우리 시스템에서는 OpenCode를 각 세션의 샌드박스 VM 안에서 실행합니다. Modal VM이 시작되면, OpenCode 서
버  프로세스를  해당  프로젝트  디렉토리에서  구동시키고  (예:  opencode --headless 모드),  이  서버는
Cloudflare Durable Object (또는 API 서버)의 지시에 따라 LLM 프롬프트를 처리하게 됩니다. OpenCode가 실행
되면, 이 에이전트에게 세션 컨텍스트(시스템 프롬프트)를 설정합니다. 여기에는 현재 프로젝트의 정보, 사용 가능한 커
스터마이즈된 툴 목록과 사용 방법, 그리고 주어진 사용자 요청이 포함됩니다. 예를 들어 시스템 프롬프트에는 “너

파일 읽기/검색 툴: 코드베이스 내 파일을 열거나 프로젝트 전체를 검색할 수 있습니다.

파일 편집 툴: 전달된 수정 내용(diff)을 적용하여 파일을 편집합니다. OpenCode의 edit 툴이 이 역할을 하
며, LLM이 생성한 패치를 실제 코드에 반영합니다. 
셸 명령 실행 툴: bash 툴을 통해 테스트 실행 (npm run test, pytest 등), 빌드 (npm run 
build), 애플리케이션 구동 (npm start), 린트 등 다양한 명령을 실행할 수 있습니다. 에이전트는 이
를 통해 테스트 통과 여부를 확인하거나 애플리케이션을 실행해 볼 수 있습니다. (시스템 프롬프트에 이러한 명
령 사용 방법과 주의사항을 명시해 LLM이 효율적으로 활용하도록 합니다.) 
테스트/CI 결과 확인 툴: 빠른 피드백을 위해 로컬에서 단위 테스트를 실행하지만, 통합테스트나 기타 CI 파이프
라인은 PR 생성 후 CI 상태 򻹧를 통해 알 수 있습니다. 이를 위해 GitHub API를 폴링하거나 Buildkite API 등
을 조회하는 툴을 만들 수 있습니다. 
로그 조회 툴: Sentry의 프로젝트 API를 호출해 최근 오류 이벤트를 가져오거나, Datadog 쿼리를 통해 특정 메
트릭이나 로그를 검색하는 툴입니다. 예를 들어 "query_sentry('error_id_123')" 식으로 호출하
면, 해당 오류의 스택트레이스를 반환하여 LLM이 버그 원인을 파악하도록 도와줍니다. 
Feature Flag 툴: LaunchDarkly 등에서 현재 특정 기능 플래그가 ON/OFF인지 확인하는 API 호출 툴입니다.
플래그 상태에 따라 코드를 다르게 처리해야 할 때 활용합니다. 
브라우저 동작 툴: 프론트엔드 변경을 검증하기 위해, 샌드박스 VM 내에 머리없는 브라우저(예: Puppeteer
or Playwright)나 브라우저 세션 스트리밍 환경을 마련해 둡니다. 에이전트는 open_page(url) 같은 툴
을 통해 로컬에서 앱을 띄워 특정 URL을 열고, take_screenshot(selector) 등의 툴로 화면을 캡처할
수 있습니다. 이렇게 얻은 스크린샷은 Cloudflare DO를 통해 사용자에게 전달되고, LLM도 원하는 경우 이 이
미지를 분석하거나 비교할 수 있도록 멀티모달 모델을 사용할 수 있습니다. (초기에는 이미지를 바로 분석
하지 않고 비교용 참고만 할 수도 있지만, 멀티모달 LLM을 붙이면 디자인 스펙과 스크린샷 비교도 가능해집니
다.) 
세션 스폰/관리 툴: 에이전트가 필요한 경우 새로운 세션을 생성하는 spawn_session(repo, task) 툴
을 가집니다. 이를 호출하면 백엔드 API가 다른 레포지토리 혹은 동일 레포지토리의 별도 분기에 새로운 세션을
시작하도록 합니다. 예를 들어 주요 서비스 코드를 수정하다가, 관련된 라이브러리 레포지토리도 변경이 필요하
면 새로운 에이전트를 띄워 거기서 작업하게 할 수 있습니다. 또한 
check_session_status(session_id) 툴로 해당 에이전트의 진행 상황(완료/진행중 여부, 결과 요
약)을 받아와 메인 에이전트 흐름에 반영합니다. Frontier급 LLM들의 자기제어 능력을 믿고, 무분별한 세션 생
성은 하지 않도록 프롬프트에 제약을 줄 뿐 별도 강제 제한은 두지 않습니다. 필요시 사용자가 대화로 “더 이상
세션 만들지 마” 식으로 제어할 수도 있습니다.
에이전트 LLM은 이러한 도구들을 사용해 스스로 개발循环을 진행합니다. “버그를 수정해줘”라는 요청이 주어지면, 관
련 코드를 read_file로 읽고 문제를 분석한 뒤, 수정이 필요하면 edit_file을 통해 코드를 고칩니다. 곧바로
run_tests를 실행해 모든 테스트가 통과하는지 확인하고, 실패하면 에러 내용을 보고 추가 수정을 합니다. 오류 로
그가 필요하면 query_sentry를 호출해 상세 정보를 얻기도 합니다. UI 변경이라면, open_page로 앱을 열고
take_screenshot으로 이미지를 찍어본 후 사용자에게 “이전과 비교해 버튼 색상이 파란색으로 변경되었음을 확
인했습니다” 같은 메시지를 줄 수 있습니다. 이처럼 코딩→검증→수정의 루프를 사람 개입 없이 반복함으로써, 에이전
트는 사람 개발자와 유사하게 일하지만 훨씬 빠른 속도로 시도와 오류를 극복합니다. AI가 이러한 과정을 통해
마치 “전체 개발팀”처럼 자율적으로 일할 수 있다는 평도 나오고 있습니다.
마지막으로,  에이전트가  변경을  완료하면  bash 툴로  git add . && git commit -m "AI: fix 
bug ..." 등을 수행해 변경분을 커밋하고 원격 브랜치에 push합니다. 여기까지가 에이전트의 역할이고, 그 다음 단
계인 PR 생성은 백엔드 API 레이어가 담당하게 됩니다.

고,  성능과  비용을  보며  GPT-5.x  등  최신  프론티어  모델을  적용합니다.  추후  사내  전용  모델을  도입하더라도
OpenCode의 추상화 덕에 쉽게 교체 가능합니다. 필요에 따라 인코딩 컨텍스트나 비용 제약에 맞춰, 프롬프트를 요약
하는 기능이나, 대형 맥락이 필요한 경우 벡터 DB를 붙여 코드 임베딩 검색 등도 고려할 수 있지만, 우선은 에이전트 자
체 능력을 최대한 활용하는 방향으로 설계합니다.
세션 관리 및 API – Cloudflare Durable Objects 활용
에이전트가 코드 작업을 수행하는 동안, 사용자와의 인터페이스를 원활히 하고 여러 세션을 병렬 관리하려면, 중앙 세션
관리 계층이 필요합니다. 여기서는 Cloudflare Workers + Durable Objects(DO)를 활용해 API 서버 겸 세션 관리
기능을 구현합니다. Durable Objects는 Cloudflare 엣지 네트워크 상에서 고유한 ID를 가진 상태ful 객체로 동작하
며, 각 객체당 단일 스레드 모델을 제공하여 동시성 문제 없이 상태를 다룰 수 있습니다. 우리 시스템에서 각 세
션(에이전트 인스턴스)마다 하나의 Durable Object를 매핑하여 사용합니다.
주요 역할과 구현사항:
세션 상태 저장 및 동기화: Durable Object는 내부에 SQLite DB 또는 메모리 상태를 보존할 수 있습니다. 이
를 통해 에이전트 세션의 대화 내역, 파일 변경 이력, 로그, 메트릭 등을 저장합니다. 또한 동일 세션에 연결된
여러 클라이언트 간에 이러한 상태를 공유·동기화합니다. (Cloudflare D1이라는 SQLite 서비스와 DO를 결합
하면 각 DO별로 SQLite DB를 가질 수 있습니다.) 
실시간 스트리밍 & WebSocket: Durable Object는 WebSocket 연결 관리를 할 수 있으며, Cloudflare
Agents SDK를 사용하면 Idle 시 자동 Hibernate 기능이 있는 WebSocket을 쉽게 구현할 수 있습니다.
이는 에이전트가 많은 토큰을 스트리밍할 때 각 클라이언트와 DO간 WebSocket으로 중계하면서도, 비활성 시
에는 DO 인스턴스를 일시적으로 내려 비용을 아끼는 이점이 있습니다. 에이전트가 샌드박스에서 메시지를 보
낼 때, DO는 해당 세션의 모든 연결된 클라이언트 (Slack, Web UI 등)의 소켓에 동일한 스트림 데이터를 전달
합니다. 또한 사용자가 보낸 프롬프트도 DO를 통해 에이전트에게 전송됩니다 (예: DO가 HTTP 요청으로 샌드
박스의 OpenCode 서버 endpoint를 호출하거나, 반대로 에이전트 프로세스가 DO에 장기 연결해 명령을 기
다리는 방식). Cloudflare Agents SDK는 이러한 패턴(프록시, 브로커)을 지원하므로 활용합니다. 
프롬프트 처리 흐름 제어: 한 세션에 사용자가 여러 프롬프트를 연달아 보낼 수도 있고, 여러 사용자가 동시 입
력할 수도 있습니다. Inspect(레퍼런스 시스템) 사례에서는 프롬프트를 큐에 쌓아 순차 처리하도록 했습니다.
따라서 DO는 만약 에이전트가 현재 어떤 프롬프트 작업을 수행 중일 때 신규 프롬프트가 도착하면 대기열에 넣
습니다. 기존 작업이 완료되면 대기 중인 프롬프트를 순서대로 에이전트에 전달합니다. 이렇게 하면 혼선 없이
진행되고, 현재 작업 중에도 다음에 할 일에 대한 논의를 Slack 등에서 미리 이어갈 수 있는 장점이 있습니다.
(반대로, 필요하다면 구현상 플래그로 즉시 삽입 모드도 고려 가능하나 기본은 순차 처리로 합니다.) 또한 DO를
통해 에이전트 작업 중단 기능도 구현합니다. 사용자가 강제로 스톱을 누르면 DO가 해당 세션에 cancellation
신호(예: OpenCode API에 중단 명령)를 보내서, 현재 연산을 중지시키고 다음 프롬프트 대기로 넘깁니다. 
API 엔드포인트: Durable Object/Workers는 일반 HTTP 요청도 처리할 수 있으므로, 세션 생성/제어를 위한
API를 제공합니다. 예를 들어 Slack 봇이 "POST /api/session/start"를 호출하면, 요청 바디에 담긴
repo 정보로 새로운 DO 인스턴스를 만들고 Modal API를 호출해 샌드박스 VM을 생성합니다. 또한 
"POST /api/session/{id}/prompt"로 프롬프트를 전송하거나, "GET /api/session/{id}/
status"로 현재 상태(예: 진행 중, 대기 중, 완료됨, PR 링크 등)를 질의할 수 있습니다. 이러한 API는 모든 타
입의 클라이언트에서 공통으로 사용하며, 인증 토큰이나 세션 식별자를 통해 접근 제어합니다. 
세션 간 통신: 앞서 에이전트 spawn_session 툴에 대해 말한 것처럼, 한 DO(세션)에서 다른 DO를 생성하거
나 메시지를 보내는 기능이 필요합니다. Durable Object 간에는 Cloudflare 내부 RPC로 메시지를 보낼 수 있
으므로, 예를 들어 spawn_session 호출 시 현재 DO가 새 DO를 생성하고, 생성된 세션 ID를 에이전트에
게 반환합니다. 이후 주기적으로 현재 DO가 자식 세션 DO에게 상태를 물어보거나, 자식 세션이 완료 시 부모에
게 이벤트를 보내주는 식의 세션 트리 통신을 구현합니다. (이 역시 Agents SDK의 멀티에이전트 패턴과 유사합
니다.) Frontier 모델의 추론에 따르면, LLM 스스로 이런 병렬 구조를 잘 활용할 수 있으므로 큰 문제가 없을 것
입니다.

클라우드 인프라 측면에서, Cloudflare Workers+DO 조합은 전세계 엣지 로케이션에서 동작하므로 사용자(조직)의 지
리적 위치에 상관없이 빠른 응답을 보장합니다. 또한 DO는 고유 세션 단위 격리로, 수백 세션이 병렬로 돌아가도 각 세
션의 로직이 간섭 없이 따로 실행됩니다. WebSocket 기반 스트리밍도 Cloudflare 네트워크가 안정적으로 중계해
주므로 실시간 업데이트 경험을 제공하기 좋습니다. 비용 측면에서도, Workers는 사용한 연산시간만큼만 과금되고 I/O
대기시간 등은 청구되지 않아 경제적입니다. 특히 에이전트 응답을 기다리는 동안에는 CPU를 소모하지 않으므로,
DO가 idle 하다 Hibernate되면 사실상 비용이 매우 낮습니다.
정리하면, Cloudflare Durable Objects와 Agents SDK를 활용한 세션 관리는 확장성, 성능, 편의성 면에서 최적입니
다. 각 세션 DO는 작은 컨트롤러로 기능하며, 실제 코드 작성과 검증 작업은 Modal VM의 에이전트가 수행, 이 둘이 합
쳐 하나의 완결된 에이전트 세션을 이룹니다.
협업 모드와 멀티플레이어 세션
우리 시스템의 강력한 차별점 중 하나는 멀티플레이어 협업 세션 기능입니다. 이는 여러 사용자가 하나의 에이전트 세션
에 참여하여 함께 AI와 대화하고 코딩 작업을 진행하는 것을 의미합니다. 이를 통해 다음과 같은 시나리오가 가능해집니
다:
비개발자의 참여와 교육: 제품 관리자(PM)나 디자이너도 개발자와 같은 세션에 들어와 에이전트에게 질문하거
나 작은 수정사항을 요청할 수 있습니다. 개발자는 그 자리에서 AI와 함께 반영해주면서 비개발자에게 AI 활용
방법을 가르쳐줄 수도 있습니다. 
라이브 QA/버그바운스: 테스트 엔지니어나 QA가 앱을 사용하며 발견한 버그를 즉시 세션에 공유하면, 에이전
트가 고치고, 다른 동료도 그 세션을 보며 의견을 줄 수 있습니다. 티켓으로 남겨놓고 나중에 처리하는 대신 실
시간으로 모두가 개선 작업에 참여하는 형태입니다. 
PR 리뷰 보조: 한 개발자가 작성한 PR을 다른 개발자가 리뷰하면서, 필요한 수정사항을 에이전트에게 바로 시
켜서 적용하게 할 수 있습니다. 리뷰어와 에이전트가 짝을 이뤄 수정한 후, 원 저자에게 다시 보내는 대신 바로
리뷰어의 커밋으로 PR을 업데이트할 수도 있습니다. 
AI 페어프로그래밍: 두 명 이상의 사람이 동일 세션에서 AI와 페어 프로그래밍을 진행할 수 있습니다. 서로 아이
디어를 주고받으며, AI가 그에 맞춰 코드를 작성해 줍니다.
이러한 협업을 가능케 하려면, 세션의 상태와 컨텍스트가 모든 참가자에게 공유되고, 입력에 작성자(사람) 정보가 붙어
야 합니다. 우리의 Durable Object 기반 설계는 기본적으로 여러 WebSocket 클라이언트를 연결시킬 수 있으므로, 한
세션에 N명의 사용자가 동시에 붙는 것이 가능합니다. 구현 세부사항은 다음과 같습니다:
동시 클라이언트 연결: DO는 세션당 고유 ID를 가지고 있고, 이 ID를 알고 있는 사용자라면 (권한만 있다면)
WebSocket이나 HTTP를 통해 참여할 수 있습니다. Slack 채널에 공유된 세션이든, 웹 대시보드에 나열된 세
션이든 버튼을 통해 진입하면 해당 DO에 소켓 연결하여 실시간 스트림을 받게 됩니다. 
프롬프트에 작성자 태그: Durable Object API는 각 메시지에 메타데이터를 첨부하여 에이전트에 전달할 수 있
습니다. 우리는 프롬프트를 보낼 때 author=user123와 같은 식별을 포함시키고, 에이전트의 시스템 프롬
프트에도 이를 반영합니다. 즉, LLM에게 "여러 사용자가 대화에 참여하고 있으며, 각 요청은 [이름]이 한 것이
다"라고 알려주어, 만약 필요하면 이를 출력에 활용하도록 하는 것입니다. (예: 에이전트가 “@김PM 님, 말씀하
신 변경을 적용했습니다”처럼 답하게 할 수도 있지만, 보통은 크게 상관없이 동작할 것입니다.) 
UI 표시: 웹 인터페이스나 Slack에서는 메시지 옆에 사용자 이름/아바타를 표시해서 누가 입력했는지, AI 응답
은 어떤 명령으로 인한 것인지 투명하게 보여줍니다. Slack의 경우 쓰레드에서 여러 사람이 봇과 대화하면 이미
자동으로 유저명 표시가 되므로 자연스럽습니다. VS Code 공유 세션처럼, 웹 IDE 편집에서도 어떤 사용자가 타
이핑한 건지 컬러 커서 등으로 표현할 수 있습니다. 
권한 관리: 기본적으로 같은 조직 내부라면 세션 공유에 큰 문제는 없겠지만, 필요한 경우 세션 owner가 초대
링크를 주거나, 사전에 정의된 팀만 접근 가능하도록 제한을 둘 수 있습니다. (DO ID자체를 UUID로 만들고 추

프롬프트 Attribution (결과 소유): 에이전트가 작성한 최종 커밋이나 PR에 대해, 누가 이 변화를 주도했는지
남기는 것도 고려합니다. 예를 들어 PR 본문에 “Co-authored-by: Alice (prompt) / Bob (review)” 식으로,
세션 참여자 이름들을 남겨두면 추후 추적에 도움이 됩니다. 
데이터 모델 측면에서, 처음부터 세션과 사용자 관계를 1 대 N으로 설계하면 됩니다. Session 엔티티에 현재 참여자 리
스트를 가지고 있고, Durable Object 메모리에도 연결된 소켓들의 사용자 식별을 매핑해두는 식입니다. 그리고 요청을
받았을 때 해당 세션이 특정 사용자 전용이라는 가정만 안 하면 되기에, 코드 구현 난이도는 높지 않습니다. 특히
Cloudflare Agents SDK는 이러한 멀티유저 시나리오를 염두에 두고 WebSocket 브로드캐스트나 state 관리 예제를
제공하고 있으므로 이를 참고합니다.
결과적으로, 협업 모드 지원은 사용자들에게 AI 에이전트를 함께 활용하는 새로운 방식을 열어줍니다. 이는 단순한 생산
성 향상을 넘어 팀 커뮤니케이션 방식 자체를 바꾸는 효과가 있을 것으로 예상합니다.
보안과 인증 (Authentication & Security)
코드베이스 접근 및 PR 작성을 수반하는 도구인 만큼,  사용자 인증과 권한 처리는 매우 중요합니다. 우리는 주로
GitHub 인증을 사용하고, 사내 도구로 쓸 경우 사내 SSO나 OAuth2를 연동합니다. 기본 원칙 및 구현은 다음과 같습
니다:
GitHub OAuth 로그인: 웹 인터페이스나 Slack 봇에서 사용자를 식별하기 위해, GitHub 계정으로 OAuth 로
그인 절차를 거칩니다. 이를 통해 사용자별 GitHub 토큰을 확보할 수 있고, 사용자 조직/팀 정보도 확인해 세션
접근 권한을 제어합니다. Slack의 경우도 슬래시 커맨드나 DM 시작 시 GitHub 계정과 연동하도록 유도합니다.
PR 작성 시 사용자 계정 사용: 에이전트가 코드를 수정한 후 PR을 열 때, 반드시 사용자의 GitHub 권한으로
PR을 생성합니다. 이는 Git 규정상 “본인이 작성하지 않은 코드를 PR로 제출할 때 반드시 리뷰/승인이 필요”하
게 하거나, 최소한 본인 PR은 다른 사람이 Approve해야 머지되도록 설정하기 위함입니다. 만약 에이전트 자
체 계정(봇 계정)으로 PR을 만들면 해당 사용자가 자기 PR을 승인할 수도 있어 위험합니다. 그러므로 샌드박스
에서 commit/push는 임시 봇 토큰으로 하되, PR 생성 호출은 API 서버가 사용자 OAuth 토큰으로 GitHub
API를 호출하여 생성합니다. 이렇게 하면 PR의 author가 실제 사용자로 표시되고, 정상적인 코드 리뷰 프로세
스와 호환됩니다. 
GitHub 웹훅 연동: GitHub의 webhook을 받아, PR 상태 변화나 커밋 푸시 이벤트 등을 시스템에 반영합니
다. 예를 들어 PR이 병합(Merge)되면 해당 세션을 종료하거나, 닫힘(Closed)되면 세션을 보류 상태로 두는
등의 처리입니다. 또한 커밋이 추가되었을 때 CI 상태를 가져와 세션에 알려줄 수도 있습니다. 이 webhook은
Cloudflare Worker 엔드포인트로 받아 Durable Object에 전달하거나 별도 처리를 합니다. 
Slack/App 권한 범위: Slack 봇이나 Chrome 익스텐션 등은 내부 서비스라 하더라도 최소 권한 원칙으로 구
성합니다. Slack은 특정 채널에만 설치하거나 봇이 DM으로만 응답하게 하는 등 제한하고, Chrome 익스텐션
도 특정 도메인(예: 회사 제품 도메인)에서만 작동하도록 설계합니다. 
데이터 접근 통제: 에이전트가 접근하는 Sentry, Datadog, LaunchDarkly 등의 API 키는 읽기 전용 권한으로
제한하고, 필요한 프로젝트 scope만 부여합니다. 또한 에이전트 시스템의 환경변수로 주입하지 않고, 특정 툴
실행시에만 키를 불러 써서 LLM이 직접 키를 노출하거나 악용하지 못하게 합니다. (예를 들어 
query_sentry 툴 구현부에서만 Sentry 키를 참조하고, LLM이 키값을 볼 일은 없도록 함) 
사고 방지 장치: Frontier LLM의 능력을 신뢰하지만 만약의 경우를 대비해, 에이전트가 위험한 명령을 수행하
려 할 때 사용자 컨펌을 받는 장치를 넣습니다. 예: bash 툴로 rm -rf / 혹은 데이터베이스 초기화 등을
시도하면 즉시 중단시키고 사용자에게 확인을 구합니다. OpenCode의 시스템 프롬프트에도 "위험한 변경을
가할 때는 반드시 사전에 설명하고 진행하도록" 가이드가 포함되어 있습니다. 이러한 규칙을 추가해
안전망을 구성합니다. 
요약: 사용자는 GitHub 인증을 통해 자신의 세션을 시작하고, 에이전트는 사용자의 권한으로만 코드 변경 사항을 시스
템에 반영합니다. 모든 중요 활동(commit, PR 생성 등)은 audit log를 남겨 추적 가능하게 하고, 필요시 관리자 권한
으로 특정 사용자의 에이전트 사용을 제한하거나 모니터링할 수 있게 합니다. 이러한 보안/인증 조치는 AI 에이전트가
조직 내에서 신뢰 받고 안전하게 사용되도록 만드는 필수 요소입니다.

Slack 통합 (Slack Bot Interface)
회사의 많은 업무 대화가 이루어지는 Slack에 에이전트를 접목하면 높은 접근성과 바이럴 효과를 얻을 수 있습니다. 사
용자는 개발 IDE나 터미널을 열지 않고도 Slack 메시지 몇 줄로 버그 수정이나 간단한 기능 추가를 에이전트에게 시킬
수 있고, 다른 동료들도 그 대화를 보며 학습하게 됩니다. Slack 통합을 구현하는 주요 사항은 다음과 같습니다:
봇 기본 설정: Slack에 사내 봇 앱을 생성하고, 필요한 OAuth 범위(chat:write, commands 등)를 부여합니다.
설치는 워크스페이스 관리자 승인 후 진행합니다. 봇은 1대1 DM으로도 대화할 수 있고, 특정 채널에 초대되어
사용할 수도 있게 합니다. 
자연어 명령 처리: 사용자가 봇에게 명령을 보낼 때 별도의 슬래시 커맨드 문법을 강제하지 않습니다. 일반 대화
형태로 “에이전트야, X 서비스에서 Y 버그 좀 수정해줘”라고 보내면, 백엔드가 이를 해석하여 동작하게 합니다.
이를 위해 빠른 LLM 기반 분류기를 사용합니다. 예컨대 GPT-4의 경량 버전(또는 GPT-3.5)에게 프롬프트 분류
를 맡깁니다. 입력 메시지, 대화 스레드 상위 맥락, 채널 이름 등을 조건으로, 사전에 정의한 레포지토리 목록 중
해당 요청을 처리할 레포지토리/프로젝트를 예측합니다. 프롬프트 예시로 “결함 수정 요청은 백엔드 레포지
토리, 버튼 색 변경은 프론트엔드 레포지토리” 등 힌트를 주고, 모델이 repo 이름 또는 'unknown'을 답하
게 합니다. 만약 모델이 unsure하면, 봇은 사용자에게 “어느 프로젝트인지 알려주세요: (리스트)”라고 물어보
게 합니다. 이 과정을 통해 사용자는 레포 이름을 일일이 언급하지 않고도 편하게 요청할 수 있습니다. 
세션 생성 및 응답 흐름: 레포지토리가 결정되면, Slack 봇은 우리의 API (Cloudflare Worker)를 호출해 새 세
션을 생성합니다. 이때 세션 생성 API는 GitHub 사용자 인증 정보와 레포 정보를 받아 Modal 샌드박스를 기동
하고 Durable Object를 마련합니다. Slack 봇은 해당 세션 ID를 내부적으로 저장하고, 사용자의 Slack 쓰레드
<-> 세션 ID를 매핑해둡니다. 이제 유저가 Slack에 보낸 요청을 프롬프트로 세션에 전달합니다. 
에이전트가 작업을 시작하면, 봇은 즉각 사용자에게 “: 로딩중:” 같은 이모지 리액션을 추가하거나, 진행상황을
알리는 메시지를 답장합니다. (예: “AI 에이전트가 <레포지토리>에서 작업을 시작했습니다. 잠시만 기다려주
세요...”) 
에이전트가 중간에 중요한 작업을 할 때 Slack으로 알려주도록 설정합니다. 이를 위해 에이전트에게 Slack 전
용 툴을 하나 제공하거나, 또는 DO가 에이전트 로그를 모니터링하다가 특정 이벤트(예: 테스트 실행 시작/완료,
브라우저 검증 완료 등)에 Slack 메시지를 보냅니다. 예를 들어 테스트 실패 시 봇이 “  테스트가 실패했습니다.
원인을 조사 중...” 혹은 테스트 성공 시 “  모든 테스트 통과! PR을 준비합니다.” 등의 상태 업데이트 블록을 편
집하여 표시합니다. Slack의 Block Kit UI를 활용해, 작업 중인 레포지토리명, 브랜치명, PR 링크 등을 깔끔한
양식으로 보여줍니다. 
에이전트 작업 결과가 나오면 (예: PR 생성됨), 최종 요약 메시지를 Slack에 보냅니다. “AI 수정 완료 – PR 
#123 생성되었습니다. 요약: ~~” 형태로 제목, 변경 요약, 스크린샷 등을 포함합니다. 그리고 봇의 로딩 리액션
은 제거하거나 완료 이모지(예: :white_check_mark:)로 교체합니다. 
대화 계속 및 멀티턴: Slack 쓰레드에서 사용자가 추가로 댓글을 달면, 해당 세션에 후속 프롬프트로 보내집니
다. 예를 들어 “테스트도 업데이트해줘”라고 쓰면 같은 세션에 전달되어 연속 작업을 합니다. 이러한 멀티턴 대
화를 통해 하나의 Slack 스레드 = 하나의 에이전트 세션으로 동작합니다. 다른 사용자가 그 스레드에
mention하면 동일 세션 협업으로 간주됩니다. 
커스텀 이모지와 재미 요소: Ramp 사례에서 처럼, 우리도 봇이 메세지에 표준 이모지만 쓰는 대신 회사 문화에
맞는 맞춤 이모지를 사용하게 해봅니다. 예를 들어 진행중 표시로 회사 로고 움직이는 이모지, 완료 표시로 박수
치는 캐릭터 이모지 등을 셋업합니다. 이는 사용자 경험을 더욱 친근하게 만들어주고, 사람들이 봇 대화를 재미
로 구경하게 하는 효과도 있습니다. 
오류 대응: 만약 에이전트가 실패하거나 예기치 못한 상황이 생기면, 봇은 적절한 사과 또는 안내 메시지를 보내
고, 필요시 세션 로그나 에러 정보를 개발팀에게 DM으로 전송해 디버깅할 수 있게 합니다. Slack은 조직내 사
용 빈도가 높기 때문에, 안정성에 특히 신경써서 사용자를 당황시키지 않도록 합니다.
Slack 통합을 통해 사용자는 “대화를 하듯 코드를 고치는” 새로운 경험을 얻게 됩니다. 또한 Slack 공간에서 AI 에이전
트가 활약하는 모습을 다른 멤버들이 보게 되면서, 점차 사용법을 학습하고 자발적으로 활용하는 문화가 퍼질 것으로 기
대됩니다. (Ramp 내부에서도 이를 통해 빠르게 사용률이 높아졌다고 합니다.)

웹 인터페이스 (Web Client)
전문 개발자나 테크에 익숙한 사용자들은 좀 더 정교한 인터페이스에서 에이전트를 사용하고 싶어할 수 있습니다. 이를
위해 리치 웹 애플리케이션 클라이언트를 제공합니다. 기술 스택은 React (TypeScript)로 구현하고, 디자인은 내부 개
발 도구 느낌으로 VS Code와 코드 리뷰 UI의 장점을 조합합니다. 주요 기능은 다음과 같습니다:
세션 리스트 및 생성: 웹 대시보드에 로그인(GitHub OAuth)하면, 좌측에는 사용자가 참여한 세션 목록(진행
중/최근 완료)이 보입니다. 새 세션을 생성하려면 우상단 “새 작업 시작” 버튼으로 레포지토리와 간단한 초기 프
롬프트를 입력받아 시작할 수 있습니다. (또는 Slack처럼 자연어로 적으면 레포 분류기를 돌려주거나, 아예 레
포를 드롭다운으로 선택하게 할 수도 있습니다.) 
채팅 패널: 화면 중앙에는 Slack과 유사한 채팅 인터페이스가 있어서, 사용자와 AI 에이전트의 메시지를 실시간
스트리밍으로 보여줍니다. 토큰이 생성될 때마다 흐르는 형태이며, 진행중 표시 등을 UI로 보여줍니다. 사용자
는 하단 입력창에 프롬프트를 적어서 엔터로 보낼 수 있고, Markdown 코드 블록 렌더링, 링크, 이미지 등이 지
원됩니다. 
에디터 패널 (웹 기반 VS Code): 화면 우측(또는 좌측)에 코드 에디터 뷰어를 포함합니다. 이는 사용자가 에이
전트가 편집한 파일을 열람하거나, 필요 시 직접 편집할 수 있게 합니다. 구현은 오픈소스 Monaco Editor(VS
Code의 에디터 컴포넌트)나 CodeMirror 등을 활용합니다. 더 나아가 live coding이 가능하도록, 아예 세션
의 샌드박스와 연결된 웹 VS Code 서버(code-server 등)를 띄워 iframe으로 제공할 수도 있습니다. 사용자
가 웹 IDE에서 코드를 고치면 그 diff를 에이전트도 인지하여 계속 작업을 이어가게 하거나, 사용자가 “내 변경
도 함께 커밋” 옵션을 통해 AI 결과물에 포함시킬 수도 있습니다. 
라이브 프리뷰/데스크톱 스트리밍: 프론트엔드 프로젝트의 경우, 세션 VM에서 개발 서버를 띄워 Live
Preview URL을 제공하거나, VM의 데스크톱 환경(브라우저)을 원격 스트림하는 기능이 유용합니다. 예를 들
어 VNC 기반으로 VM 화면을 웹에 넘겨주면, 사용자는 AI가 브라우저에서 수행하는 동작(클릭, 내비게이션)을 
실시간으로 지켜볼 수 있습니다. 이는 마치 화면 공유하듯 에이전트의 테스트 과정을 보여주어 신뢰감을 줍니
다. (실제 Inspect 시스템도 에이전트가 UI 테스트를 하는 장면을 세션 UI에서 볼 수 있다고 합니다.) 또한 에이
전트는 전후 상태 스크린샷을 찍어 PR 설명에 붙여주는데, 웹 UI에서도 “Before/After” 이미지를 비
교 뷰어로 제공하면 좋습니다. 
세션 제어 버튼: 채팅 인터페이스 상단이나 적당한 위치에 제어용 버튼들을 둡니다. 예: “중단/취소”, “다시 실
행”, “PR 보기”, “세션 종료” 등이 있습니다. 취소를 누르면 DO를 통해 에이전트 작업을 stop시키고, 다시 실
행은 마지막 프롬프트를 처음부터 재시도(예: 다른 모델로)할 수도 있습니다. PR 보기는 링크를 열거나, 간단한
diff를 모달로 띄워줄 수도 있습니다. 세션 종료는 명시적으로 VM을 중지하고 리소스 해제하는 용도입니다. 
모바일 대응: React 앱은 Responsive 디자인으로 만들어 모바일 브라우저에서도 사용 가능하게 합니다. 󵿯
근길이나 긴급상황에 휴대폰으로도 세션에 접속해 진행상황을 보거나 간단한 명령을 내릴 수 있도록 고려합니
다. (Ramp Inspect도 모바일 웹을 염두에 두었다고 합니다.)
추가로, 조직-wide 대시보드를 웹 앱에 포함해 사용 통계 및 성과를 시각화합니다. 이를 통해 모든 구성원이 에이전트
도구의 효과를 한눈에 볼 수 있습니다. 예를 들어:
전체 에이전트 세션 수 (일별/주별 트렌드 그래프) 
에이전트 결과로 생성된 PR 수 및 그 중 병합된 PR 비율 (성공률 지표) 
에이전트를 사용한 활성 사용자 수 (최근 5분/하루 등) 
평균 세션 소요 시간, 평균 모델 토큰 비용 등의 메트릭 
이러한 지표를 실시간 갱신되게 하여, 현재 몇 명이 에이전트를 쓰고 있는지도 보여줍니다 (예: “현재 5명의 사용자가 프
롬프트를 입력 중입니다” 등). Ramp의 경우 30% PR 비중 등을 사내에 공유하며 사용을 독려했다고 하니, 우리도 가시
적인 성과를 팀원들에게 보여줘 자연스러운 홍보 효과를 얻습니다.
정리하면, 웹 인터페이스는 단순 채팅 이상의 개발용 종합 UI로 제공하여, 사용자가 에이전트와 상호작용하면서도 코드
에 대한 통제권과 가시성을 충분히 느낄 수 있게 합니다. 이는 신뢰 구축과 복잡한 사용 사례 지원에 중요합니다.

크롬 브라우저 확장 (Chrome Extension)
비개발자나 디자이너도 AI 에이전트를 활용하여 프로덕트 UI를 직접 개선할 수 있도록, Chrome 확장 프로그램 형태의
시각적 프롬프트 도구를 제공합니다. 이 툴은 사용자가 웹사이트의 원하는 요소를 가리키며 “여기 글씨를 더 크게 하고
색을 파란색으로 변경” 같은 요청을 하면, 백엔드의 에이전트가 해당 내용을 코드 수정으로 이어주는 방식입니다. 주요
동작 원리:
React 앱 DOM 추출: 사용자가 크롬 확장 UI에서 특정 DOM 요소를 선택하면, 해당 요소의 전체 DOM 트리 구
조, 속성(props), 텍스트 내용 등을 수집합니다. 가능하면 React 개발자 도구와 통신하여 컴포넌트 이름,
props, state 등의 React 내부 정보도 얻습니다. (Ramp의 구현에서는 React 내부 디버깅 정보를 직접 활용했
다고 합니다. 외부인 경우 ReactSight나 React Grab 같은 오픈소스 도구를 활용 가능.) 
요청 전송 최적화: 이렇게 수집된 정보는 텍스트 형태(JSON 또는 HTML)로 요약하여 백엔드로 전송합니다. 화
면 스크린샷 이미지 자체는 보내지 않습니다. 이미지로 보내면 LLM이 이해하기 어려울 뿐더러 토큰도 많이 소
모되기 때문입니다. 대신 “선택된 요소의 계층 구조와 속성”을 프롬프트에 첨부해, LLM이 구조적 맥락을 이해
하도록 합니다. (예: div(id="header") -> h1(class="title"): "Welcome" 이런 식의 트리) 
백엔드 처리: 브라우저 확장으로부터 받은 요청을 처리할 전용 API 엔드포인트를 마련합니다. 이 요청에는 현재
보고 있는 웹 페이지 URL도 포함되며, 이를 통해 어느 레포지토리의 어떤 페이지인지 매핑합니다. 예를 들어
URL이 app.company.com/settings이면 프론트엔드 레포지토리로, api.company.com이면 백엔
드 레포지토리로 결정하는 식입니다 (혹은 사용자에게 확장에서 서버/클라이언트를 선택하게 할 수도 있습니
다). 
해당 레포지토리의 에이전트 세션을 생성하고, 프롬프트로 “다음 React 컴포넌트 트리에서 표시되는 ... 부분
을 수정하라”는 지시와 함께 DOM 추출 정보를 제공합니다. LLM은 이를 보고 어떤 파일(컴포넌트)과 어떤 부분
을 바꿔야 할지 추론합니다. 
에이전트가 코드를 수정하면, 브라우저 쪽에 실시간 미리보기를 보내줍니다. 이는 WebSocket을 통해 “CSS 변
경됨” 등의 이벤트를 브라우저 확장으로 전달하거나, Hot Reload처럼 변경된 JS/CSS를 인젝션하여 페이지에
바로 적용되게 할 수 있습니다. (간단히는, 변경 후 프론트엔드 서버에서 빌드된 결과를 extension이 새로고침
해 보여주는 방식도 가능) 
사용자에게 확장 UI 상에서 Before/After 화면을 비교해서 볼 수 있게 하거나, 만족하면 “확인”을 눌러 PR을 생
성하도록 합니다. 
기업 내부 배포: Chrome 확장을 직원들에게 배포할 때는 일반적으로 Chrome Web Store를 통해야 하지만,
회사 G-suite 계정으로 관리형 기기 정책(ExtensionInstallForcelist)을 사용하면 내부적으로 직접 배포할
수 있습니다. 이를 위해 CRX 패키지 호스팅 서버를 설정하고, 매니페스트 JSON에 업데이트 URL을 지정합니
다. 그러면 회사 크롬 브라우저들은 자동으로 해당 확장을 설치하게 할 수 있습니다. (이 방법은 Web Store 심
사 없이 배포할 수 있고, onboarding 없이 바로 브라우저에 아이콘이 생기므로 도입 장벽이 거의 제로가 됩니
다.) 
Chrome 확장으로 비기술 직군도 GUI 환경에서 AI 활용이 가능해지면, 사소한 텍스트 수정이나 스타일 변경 등을 개발
팀에 요청하지 않고 셀프서비스로 처리하는 문화가 자리잡을 수 있습니다. 물론 최종 머지는 여전히 개발자 리뷰를 거치
지만, 이 과정 자체가 효율화됩니다. 또한 확장 사용 사례는 곧바로 AI 에이전트의 효용을 비개발 부서에 어필하는 효과
도 있습니다.
모니터링, 로깅 및 지속적 개선
AI 에이전트 시스템을 운영하면서, 모니터링과 로그 수집은 두 측면에서 중요합니다: (1) 시스템 신뢰성 확보와 이슈 디
버깅, (2) 사용 현황 파악 및 성능 개선. 이를 위해 다음을 구현합니다:
Sentry 에러 모니터링: 에이전트 백엔드(Workers, Modal VM 코드 등)에 예외나 오류가 발생하면 Sentry로
보내어 추적합니다. 예를 들어 LLM API 호출 실패, Slack API 에러, 에이전트 툴 실행 중 발생한 예외 등을 로깅
합니다. 이를 통해 문제 발생시 개발팀이 신속히 인지하고 수정할 수 있습니다.

Datadog 메트릭: 주요 성능 지표(세션 시작 시간, 모델 응답 시간, 세션 당 토큰 사용량, 성공적으로 PR까지 간
세션 비율 등)를 Datadog 커스텀 메트릭으로 전송합니다. 대시보드에 그래프로 시각화하여, 시간 경과에 따른
추이를 봅니다. 또한 Datadog 로그를 통해 에이전트의 주요 이벤트(세션 생성, PR 완료 등)를 로그로 남기고
검색할 수 있게 합니다. 
AI 응답 로그와 재현: 각 세션의 LLM 대화 로그를 저장해 둡니다 (보안 상의 이유로 민감 정보는 필터링). 이것
은 나중에 분석이나 문제 재현에 사용합니다. 예를 들어 에이전트가 잘못된 코드를 생성했다면, 해당 대화와 프
롬프트를 리뷰하여 프롬프트 엔지니어링 개선에 활용합니다. (한편으로 GDPR 등 규제가 있다면 일정 기간 후
폐기하거나, PII는 남기지 않도록 주의합니다.) 
피드백 루프: 사용자 인터페이스 (Slack이나 웹)에 에이전트 답변에 대한 feedback을 줄 수 있는 기능을 고려
합니다. 👍/👎 리액션이나 “재시도” 버튼으로 의사를 표시하면, 이를 기록했다가 향후 모델 업그레이드나 프롬
프트 수정에 반영합니다. 또한 Slack 채널을 모니터링해 사용자가 수동으로 한 수정사항(에이전트 못 찾아서 직
접 PR한 케이스 등)을 발견하면, 이를 학습 데이터로 삼아 나중에 AI가 유사 상황에 대응하도록 할 수 있습니다.
성공 사례 공유: Monitor 시스템에서 아까 언급한 통계 외에도, 흥미로운 케이스를 캡쳐해 사내 위키나 주간 뉴
스레터로 공유합니다. 예: “지난주 에이전트가 X 기능을 5분만에 구현하여 Y팀의 큰 도움이 됨” 같은 스토리를
전파하면 더욱 활용이 늘어납니다. 이는 내부 도입 촉진 전략으로 중요한 부분입니다 (Ramp도 강제보다는 자
발적 전파에 의존했다고 합니다).
마지막으로, 지속적인 모델 및 시스템 개선을 위한 체계도 갖춥니다. 새로운 LLM이 나오면 테스트하여 교체하고, 특정
범주의 작업에서 실패율이 높으면 해당 부분에 대한 지침(예: 더 나은 테스트 생성법)을 시스템 프롬프트에 추가합니다.
툴 세트도 점진적으로 확장/조정해서, 실제 개발자들의 요구에 부응하도록 합니다. 내부 피드백 채널(Slack 채널 등)을
마련해 사용자들이 원하는 기능이나 겪은 불편을 듣고 빠르게 반영하면, 신뢰성과 효용이 더욱 높아집니다.
기술 스택 정리 (Tech Stack Summary)
위에서 언급한 구성요소들을 구현하기 위한 구체적인 기술 스택을 정리하면 다음과 같습니다:
클라우드 인프라: Modal (또는 유사한 서버리스 VM 플랫폼) + Cloudflare Workers/Durable Objects.
Modal은 컨테이너 기반 VM을 빠르게 관리하기 위한 선택이고, Cloudflare Workers는 글로벌 서버리스 환경
으로 API와 세션 관리를 담당합니다. 이 둘을 묶어 사용하는 것은 Ramp 사례에서 검증되었고, 우리도 그대로
򟻘합니다. 
샌드박스 VM 환경: Docker 컨테이너 (Linux 기반) – 각 레포지토리에 맞춰 Node.js, Python, DB, 브라우저
등 필요한 툴chain을 설치합니다. 예: 프론트엔드 레포는 Node 18+, Chrome 혹은 Playwright, 백엔드는
Python 3.10 + Postgres, 기타 microservice 특성에 맞는 언어/런타임. 모든 이미지는 Modal에서 관리하며,
30분 주기 빌드. 
AI 코딩 에이전트: OpenCode 프레임워크 – Bun (JavaScript/TypeScript Runtime) 기반 에이전트 서버를
사용합니다 . OpenCode 자체는 오픈소스이므로 포크하여 필요에 맞게 커스터마이징 가능합니다 (예: 추가
툴 등록, 프롬프트 조정 등). Bun은 Node.js보다 빠르고 경량이어서 선택되었으며, TypeScript 지원으로 플러
그인 등을 안전하게 개발 가능합니다. 
대형언어모델 (LLM): OpenAI GPT-4/GPT-5, Anthropic Claude 2 등 – 우선 API를 통해 상용 모델을 사용합
니다. OpenCode의 AI SDK로 통합되며, API 키는 안전하게 저장. Slack 레포 분류기에는 속도를 위해 
GPT-3.5 Turbo 혹은 GPT-4 32k with no chain-of-thought 등을 사용, 또는 사내 배포된 작은 모델(예:
Llama2 13B fine-tuned) 등을 활용할 수도 있습니다. Cloudflare Workers에서 AI Gateway 기능을 쓰면,
Workers 내에서 OpenAI 등 호출도 가능하므로 모델 호출은 DO나 에이전트에서 직접 하도록 합니다. 
백엔드 API 및 Orchestration: Cloudflare Workers + Durable Objects – TypeScript로 작성합니다.
Durable Object 클래스로 SessionManager를 구현하고, KV 또는 D1 DB를 사용해 세션 메타데이터 저장.
Slack 이벤트 수신용 HTTP endpoint, GitHub webhook endpoint 등도 Workers로 작성. Agents SDK 사
용으로 WebSocket, scheduling, concurrency 관리 코드 작성을 단순화합니다. 
프론트엔드 웹: React (TypeScript) + Vite 또는 Next.js – 컴포넌트 라이브러리는 상황에 따라 Chakra UI,
MUI 등 사용. 채팅 UI 구현에는 open source인 리액트-챗-ui 같은 것도 참고. Monaco Editor를 embed하여
코드보기/편집 지원. WebSocket 통신은 workers.dev의 DO와 직접 연결하거나, Apollo GraphQL
Subscriptions를 붙일 수도 있지만 가벼운 Vanilla WS로도 충분합니다.

Slack Bot: Slack API 호출은 Cloudflare Workers에서 fetch로 구현 가능하지만, 편의를 위해 Bolt (Slack
SDK)같은 건 Node.js 서버용이라 Workers와는 안 맞습니다. 그러므로 Workers에서 직접 이벤트를 받고,
Slack Web API도 fetch로 호출합니다. 이벤트 핸들링 로직은 TS로 작성. Slack에서 reply나 message
update할 때 Block Kit JSON을 수동 구성하거나, Block Kit Builder툴 써서 미리 템플릿을 만들어 코드화합
니다. 
Chrome Extension: Manifest v3 기반으로 제작. UI는 React+TS로 popup이나 sidebar 페이지 구현.
Content script로 페이지 DOM 접근 및 element picker 기능 구현(예: document.elementFromPoint
등으로 요소 선택). 선택된 DOM 정보를 BG script로 보내면, BG에서 Workers API 호출. 결과를 받아
Content script에 전달하여 DOM 업데이트. 개발 시편의를 위해 crx-webpack 또는 Vite-plugin-chrome-
extension 등을 사용해 빌드. 
CI/CD: 본 프로젝트 자체도 코드이므로, GitHub로 관리하며 Vercel이나 Cloudflare Pages로 웹 프론트 배포,
Workers CI 배포 (CLI로 publish), Chrome Extension은 CI에서 zip 만들어 내부 서버에 업로드, Modal 이미
지 빌드는 Modal 자체의 scheduler로 처리. Sentry/Datadog 키 등은 CI 시점에 시크릿 주입. 
통합 및 기타: LaunchDarkly API (Node/Python SDK) – feature flag 툴 구현에 사용. Sentry JS/Python
SDK – 에이전트 내부 오류 전송. Datadog API – metrics 전송 (Workers에서는 fetch로 Datadog HTTP API
호출). Posthog or Amplitude – 사용자 행동 추적 (원한다면). GitHub Octokit SDK (TS) – PR 생성 및 상태
򻹧. Buildkite API – CI 파이프라인 상태 확인.
언어 측면으로 보면, 백엔드 대부분은 TypeScript(Workers, OpenCode plugins 등)로 작성되고, 프론트엔드/확장은
TypeScript + React, 샌드박스 내부에서는 Node/Bun(JavaScript)와 필요 시 Python 실행도 가능 (ex: 프로젝트
코드가 Python일 경우 테스트 실행에 Python 사용). Python은 에이전트 자체 코드에는 직접 쓰이지 않지만, 만약
OpenCode를 도입하지 않고 커스텀 에이전트를 작성한다면 Python의 LangChain이나 Guidance 프레임워크를 쓸
수도 있습니다. 그러나 기존 검증된 OpenCode + Node 스택이 개발 속도와 유지보수 측면에서 유리하므로 권장 경로
를 따라갑니다. 
개발 및 배포 단계 (Implementation Phases)
마지막으로, 실제 구현을 진행하는 데 권장하는 단계별 접근은 아래와 같습니다:
MVP 세션 동작 구현: Modal을 통해 간단한 리포지토리 (예: Hello World 앱)의 이미지를 만들고, Cloudflare
DO 하나와 OpenCode 에이전트 실행을 연동하여 단일 세션에서 기본적인 파일 편집 → 테스트 실행 → 결과
스트리밍까지 동작시키는 것을 목표로 합니다. CLI 또는 간단한 web UI로 프롬프트를 넣고 에이전트 응답을 받
아보며, 전체 플로우를 검증합니다. 
핵심 툴 추가: Sentry 로그 조회, Feature flag 조회, 브라우저 스크린샷 등 중요 커스텀 툴들을 에이전트에 하
나씩 추가합니다. 각 툴이 잘 동작하는지, LLM이 이를 활용하는지 확인합니다. 이때 필요하면 프롬프트에 사용
예시를 넣어 모델이 언제 툴을 쓰면 되는지 학습시킵니다. 
Slack 통합: Slack 봇을 세팅하고, 레포지토리 분류 로직과 세션 시작/종료를 Workers API와 연결합니다. 내
부에서 테스트 워크스페이스를 만들어 개발팀이 시범 사용해보며 피드백을 받습니다. UI상의 편의 (Block Kit
메시지, 이모지 등)도 다듬습니다. 
Web UI 개발: React 기반 웹 대시보드를 구현하고, OAuth 로그인부터 세션 관리, 실시간 채팅 뷰, 코드 뷰어
등을 완성합니다. Slack과 병행해 세션을 컨트롤해보며 동기화에 문제 없는지 검사합니다. VS Code embed나
Live share 등 고급 기능은 기본이 안정된 후 추가합니다. 
Chrome Extension 개발: 크롬 익스텐션을 만들어 사내 제품에 적용 테스트합니다. UI 선택 → 세션 생성 →
코드 변경 → 결과 반영까지 end-to-end 시연해보고, 모델이 DOM 정보만으로 코드를 잘 찾아 수정하는지 실
험합니다. 필요하면 컴포넌트명과 파일명 매핑 데이터를 마련해 모델 힌트를 줍니다. 
멀티플레이어 & Auth: 다중 사용자 세션 참여 기능과 GitHub 인증/PR 로직을 완성합니다. 권한 체계를 확인
하고, 여러 계정으로 한 세션에 들어가 서로 대화하며 에이전트 사용을 실습해봅니다. PR은 실제 리포지토리의
테스트 브랜치에 열어보고 머지까지 프로세스 점검합니다. 
모니터링/안전망 추가: Sentry 오류 일부러 발생시켜 보고, Slack에서 엣지 케이스 (모델이 뭘 못 알아들을 때
등) 시나리오를 점검합니다. 잘못된 명령에 대한 차단 및 확인 흐름도 테스트합니다. Datadog에 지표가 쌓이는
지 확인합니다.

시범 운영 및 개선: 작은 팀 단위로 베타 운영을 하며 일주일~한 달 관찰합니다. 이 동안 모인 데이터로 모델 프
롬프트 튜닝, 새 툴 요청사항 반영, 버그 수정 등을 빠르게 반복합니다. Slack 등에 FAQ나 잘 되는 사례를 공유
해 흥미를 돋웁니다. 
전체 조직 확대 배포: Chrome Extension을 전체 직원 브라우저에 배포하고, Slack 봇을 기본 채널에 초대하
며, 웹 대시보드 링크도 공지합니다. 처음엔 복잡한 기능보다 “이렇게 해보세요” 식의 간단한 사용법을 전파하
고, 자연스럽게 사용이 퍼지도록 합니다. 이후에도 상시로 통계 추이를 모니터링하고, 임계점(예: PR 50% 이상
AI 작성)을 향해 개선을 지속합니다.
以上이 Ramp Inspect와 거의 동일한 서비스를 구현하기 위한 상세한 가이드입니다. 최적의 아키텍처와 기술 스택을
활용하여, 이 시스템은 개발자 생산성을 크게 높이고 새로운 협업 방식을 정착시킬 것입니다. 무엇보다도, 실제 현업 개
발자들의 요구를 반영하고 빠르게 개선해나가는 것이 성공의 열쇠입니다. 이 계획을 바탕으로 착실히 구축해나간다면,
머지않아 우리 조직에서도 “AI 개발 에이전트가 당연한 동료”가 되는 미래를 실현할 수 있을 것입니다.
