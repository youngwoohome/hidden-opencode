사내 AI 코딩 에이전트 구축 가이드 (Ramp “Inspect” 서
비스 구현)
개요:
Ramp에서 개발한 Inspect와 같은 사내용 AI 코딩 에이전트를 구축하기 위해서는, 세 가지 계층으로 구성된 시스템 아
키텍처를 설계해야 합니다. 첫째, 샌드박스 기반 실행 환경을 통해 에이전트가 안전하고 신속하게 코드를 작성/검증할
수 있도록 합니다. 둘째, API 및 세션 관리 레이어를 구축하여 여러 클라이언트 인터페이스(예: 웹, Slack, 크롬 익스텐
션 등)와 에이전트 세션 상태를 동기화합니다. 셋째, 개발자들이 일상적으로 사용하는 플랫폼에서 에이전트를 활용할 수
있도록 다양한 클라이언트 인터페이스(Slack 챗봇, 웹 UI, 브라우저 확장 등)를 제공합니다. 이 가이드에서는 요구된 모
든 기능을 포함하여, 이러한 시스템을 구현하기 위한 세부 구조와 기술 스택을 설명합니다.
1. 샌드박스 기반 개발환경 인프라 구축
왜 샌드박스인가: 에이전트를 로컬이 아닌 원격 샌드박스 VM에서 실행하면, 무제한 동시 실행과 일관된 개발환경, 그리
고 멀티플레이어 협업이 가능합니다. 각 세션은 다른 세션과 격리되어 자원을 독점하며, 실제 개발자가 쓰는 모든 도구
를 갖춘 환경에서 동작합니다. Ramp의 사례처럼, Modal과 같은 클라우드 VM 플랫폼을 사용해 이러한 환경을 필요 시
즉각적으로 띄우는 것이 핵심입니다.
이미지 레지스트리와 미리 빌드된 이미지: 신규 세션을 빨리 시작하려면 풀 개발환경을 미리 준비해두어야 합니
다. 이를 위해 레지스트리 이미지를 30분 간격 등으로 주기적으로 빌드합니다. 각 이미지에는 해당 리포지토리
의 특정 커밋 시점 코드, 모든 런타임 의존성, 초기 빌드 산출물, 그리고 애플리케이션 실행 및 테스트 캐시까지
포함합니다. 이렇게 하면 세션 시작 시 최근 이미지에서 컨테이너를 띄우기만 하면 되며, 코드가 최대 30분 정도
오래된 상태이므로 최신 브랜치와 동기화하는 데 걸리는 시간이 대폭 줄어듭니다.
스냅샷 및 복원: Modal의 파일시스템 스냅샷 기능을 활용하여, 환경 상태를 저장/복원합니다. 예를 들어:
초기 이미지 빌드 완료 후 베이스 스냅샷 저장 
에이전트가 코드 변경을 마치면 세션 완료 스냅샷 저장 
세션 중단 후 사용자가 후속 요청을 보낼 때 이 스냅샷을 복원하여 이어서 작업 
스냅샷을 사용하면 동일한 세션을 일시 중지했다가 재개하거나, 후속 프롬프트에 대해 환경을 다시 세팅할 필요 없이 곧
바로 이전 상태에서 시작할 수 있습니다.
Git 인증 및 구성: 샌드박스 내에서 코드를 򻹧아웃하고 커밋/푸시하려면 GitHub 인증이 필요합니다. 사용자
별로 GitHub OAuth 토큰을 받되, 리포지토리 읽기 전용으로는 GitHub App 설치 토큰을 활용하는 패턴을 씁
니다.  이미지  빌드  단계에서  이  App  토큰으로  저장소를  clone하고,  커밋/푸시  시점에는  에이전트가  git
config의 user.name, user.email을 실제 사용자로 설정하여 커밋합니다. 이렇게 하면 에이전트가 올린
PR도 해당 사용자 명의로 올라가며, 내부 규칙에 따라 자신이 생성한 PR을 바로 승인하는 등의 허점이 생기지
않습니다 (리뷰 프로세스 유지). 
웜 스타트(Warm Start) 전략: 세션 시작 지연을 최소화하기 위해 예열된 샌드박스 풀(pool)을 운영합니다. 자
주 사용하는 주요 리포지토리에 대해서는 미리 컨테이너를 띄워 대기시키고, 새로운 이미지가 빌드될 때마다 해
당 풀도 갱신합니다. 특히 사용자가 프롬프트를 입력하기 시작하는 순간 예측하여 백그라운드에서 해당 리포지
토리의 샌드박스를 띄우고 최신 코드를 동기화해두면, 사용자가 Enter를 치는 시점에는 이미 환경이 준비되어
있는 식입니다. 이러한 프롬프트 예측 예열(Predictive Warm-Up)은 모델 응답 속도 외의 지연을 없애주
는 핵심 최적화입니다.

파일 동기화와 접근: 대규모 저장소의 경우, 베이스 이미지 생성 이후 지난 30분 사이 변경된 파일만 동기화하
면 됩니다. 이 동기화가 완료되기 전에라도 에이전트가 작업을 시작할 수 있도록, 파일 읽기는 허용하되 쓰기는
일시 정지하는 메커니즘을 도입합니다. 즉 에이전트가 초기 분석을 할 때 최근 변경분이 아직 반영되지 않
았더라도 큰 문제는 없으므로, 읽기 작업은 즉시 진행하게 합니다. 단, 동기화 완료 전까지 파일 쓰기 작업은 대
기열에 넣었다가 동기화 완료 후 한꺼번에 적용합니다. 이러한 처리는 플러그인 등을 통해 구현할 수 있으
며, 동기화로 인한 충돌을 예방합니다.
개발 툴 설치: 샌드박스 VM에는 로컬 개발머신과 동일한 툴 세트를 설치합니다. 예를 들어, 프론트엔드 개발을
위해 Node.js와 빌드 도구(Vite 등), 백엔드 개발을 위해 Python/Go 런타임, 데이터베이스(Postgres), 워크플
로 엔진(Temporal) 등을 포함합니다. 또한 CI/CD, 모니터링 툴 연동을 위해 Sentry CLI, Datadog 에이전트,
LaunchDarkly CLI, 사내 내부 도구(예: Braintrust 지식베이스) 접근을 위한 토큰/SDK도 설치하거나 세션 환
경변수로 제공합니다. 이러한 준비로 에이전트는 개발자와 동일한 맥락과 권한으로 행동하며, 코드 작성 후 자
체적으로 검증까지 수행할 수 있습니다 (예: 테스트 실행, 플래그 값 조회 등).
➡ 기술 스택: Sandbox 인프라는 Modal의 서버리스 VM을 사용하여 구현합니다. Modal을 통해 도커라이크 이미지를
관리하고, Python이나 Bash 스크립트로 이미지를 주기적 빌드하도록 자동화합니다. 또한 Modal API를 통해 컨테이
너 생성/스냅샷/재시작을 제어합니다. 각 컨테이너 내부에는 OpenCode 에이전트 서버 (아래 섹션 참조)가 실행되며,
Git 및 각종 툴이 설치된 Linux 기반 환경입니다. 
2. AI 코딩 에이전트 코어 및 플러그인 (OpenCode 활용)
에이전트 프레임워크 선정: 에이전트의 "뇌"에 해당하는 코어 시스템은 오픈 소스 OpenCode 프로젝트를 기반으로 구
축하는 것을 권장합니다. OpenCode는 서버-클라이언트 구조로 설계된 AI 코딩 에이전트 프레임워크로, CLI/TUI나 데
스크탑 앱은 그 위에 얹어진 클라이언트일 뿐 핵심 로직은 서버로 동작합니다. 이러한 Server-First 아키텍처를 선택하
면, 한 번 만든 에이전트 로직을 Slack, 웹, IDE 등 여러 인터페이스에서 재사용할 수 있고, 모든 인터페이스에서 일관된
동작을 보장할 수 있습니다. OpenCode는 또한 플러그인 시스템과 이벤트 훅을 제공하여, 우리 시스템에 필요한 맞춤
기능을 쉽게 추가할 수 있습니다 (예: 파일 동기화 완료 전 쓰기 차단 등).
자기 자신을 이해하는 에이전트: OpenCode의 또 다른 장점은 에이전트가 자신의 코드베이스를 읽어 이해할
수 있다는 것입니다. 모델이 문서로만 추론하는 대신, 모호한 동작은 에이전트가 자신의 소스코드를 직접 열람
하여 정확한 동작 방식이나 API를 확인하게 함으로써, 󳰜이나 환상(hallucination)을 줄일 수 있습니다. 이는
에이전트 개발/디버깅 시에도 큰 도움이 됩니다.
코드 작성 + 검증 능력: Inspect와 같은 에이전트는 단순히 코드 스니펫을 제안하는 것을 넘어서, 자신이 작성
한 코드의 효과를 검증하는 단계까지 수행합니다. 이를 위해 OpenCode 에이전트에 다양한 툴(plugin)과 명
령 실행 권한을 부여해야 합니다. 예를 들어:
백엔드 변경 시: 테스트 스위트를 실행하고 결과 확인, 관련 로그/모니터링 (Sentry, Datadog) 조회,
LaunchDarkly 등 피처 플래그 상태 검사 등을 수행하도록 커맨드라인 툴을 호출하는 기능.
프론트엔드 변경 시: 개발 서버를 빌드/실행한 뒤 헤드리스 브라우저로 지정된 UI 경로를 열어 스크린샷을 촬영
하거나 DOM을 검사하는 기능. UI 변경 전후의 스크린샷을 비교하여 제대로 적용됐는지 확인하고, 이를 PR 설
명에 첨부하거나 Slack으로 전송.
코드 품질 검토: 에이전트가 변경한 코드에 대해 린트나 정적 분석 도구를 실행해보는 기능 (CI에서 잡힐 이슈를
미리 확인).
이러한  툴  실행은  OpenCode의  명령  실행  플러그인으로  구현할  수  있습니다.  OpenCode  에이전트  프로세스가
sandbox 내에서 쉘 명령을 실행할 수 있도록 허용하고, tool.execute.before 등의 이벤트 훅에서 특정 조건
시 동작을 가로채거나 (예: git sync 완료 전에는 write 차단) 추가 로직을 주입합니다. 예를 들어, 파일 동기화 플러

세션 병렬 생성 (Self-Spawning) 기능: 대규모 작업이나 다중 저장소에 걸친 작업을 위해, 에이전트가 다른
에이전트 세션을 스스로 생성할 수 있도록 설계합니다. 예를 들어 “백엔드와 프론트엔드 모두에 걸친 대규
모 업데이트” 작업을 하나의 세션에서 진행하기보다, 백엔드용/프론트엔드용으로 별도 세션들을 병렬로 띄워
각각 PR을 만들도록 할 수 있습니다. 이를 위해:
에이전트에게 새로운 세션을 시작하는 전용 툴(예: spawn_session)을 제공합니다. 이 툴은 API 레이어를
통해 새로운 샌드박스 세션을 띄우고, 해당 세션의 식별자(ID)를 반환합니다.
또 다른 툴은 특정 세션의 상태(예: 진행 중인지 완료되었는지, PR이 생성되었는지 등)를 조회할 수 있게 합니다
( check_session_status 등) .
프롬프트 엔지니어링 측면에서는, 언제 이러한 병렬 세션을 사용할지 모델이 결정하도록 가이드합니다. 예
컨대 “다른 저장소 조사 필요시”, “큰 변경을 작은 PR 여러 개로 쪼갤 시”, “여러 접근 방안을 동시에 시험할
시” 등에 해당 툴 사용을 고려하도록 미리 지시합니다.
최신 고성능 LLM들은 스스로 무한 증식하지 않도록 제약을 학습했기에, 과도한 세션 생성으로 시스템을 고갈시킬 위험
은 낮습니다 . 그래도 시스템 상에서는 최대 동시 세션 수 제한, 또는 관리자 알림 등의 안전장치를 두는 것이 좋습니
다.
➡  기술  스택: 에이전트  코어로는  OpenCode  (Go  기반)를  사용하고,  필요한  플러그인은  Go로  작성합니다.
OpenCode 자체가 여러 AI 모델(OpenAI GPT-4, Anthropic Claude, Google Gemini 등) 연동을 지원하므로, 사내에
서 허용된 최신 LLM API를 연결하면 됩니다. 추가 툴 호출은 OpenCode의 플러그인 또는 커맨드 바인딩 기능을
통해  구현하고,  OS  상에서  Python  스크립트나  CLI  도구를  호출하는  방식을  취합니다.  예컨대  테스트  실행은
pytest 명령 호출, 브라우저 제어는 Playwright Python 라이브러리를 호출하는 스크립트 등으로 구현할 수 있습
니다. 
3. API 레이어 및 세션 상태 관리
역할: API 레이어는 클라이언트(웹, Slack 등)와 백엔드 에이전트 세션(sandbox) 사이를 중계하고, 세션별 상태를 관리
합니다. Cloudflare Durable Objects를 사용하여 이 레이어를 구현할 수 있습니다. Durable Object는 세션마
다 독립된 저장소(예: SQLite)를 가지므로, 수백 개 세션이 병렬로 돌아가도 서로 간섭 없이 높은 성능을 유지할 수 있습
니다 . 각 DO 인스턴스는 해당 세션의 대화 내역, 진행 상태, 출력 스트림 등을 보관하면서, 여러 클라이언트로부터
들어오는 입력을 순서대로 처리합니다.
세션 상태 및 동기화: Durable Object 내부에 SQLite DB나 메모리를 이용해 대화 스레드와 에이전트 작업 상
태(예:  “코드  생성  중”,  “테스트  실행  중”,  “PR  생성  완료”  등)를  저장합니다.  클라이언트는  DO에
WebSocket  또는  SSE(Session  Event  Stream)로  연결해  실시간  스트림을  수신합니다.  Cloudflare의
Agents SDK를 활용하면, sandbox에서 출력되는 토큰들을 DO를 거쳐 클라이언트로  끊김 없이 중계하는
WebSocket 관리가 수월합니다 (비활성 시 자동 Hibernate 등). 이를 통해 사용자는 에이전트의 진행 상황을
실시간으로 모니터링할 수 있습니다 (마치 채팅하듯이 토큰이 흘러나옴).
프롬프트 처리와 대기열: 사용자가 에이전트가 작업 중일 때 추가 메시지를 보내는 경우의 처리 전략을 결정해
야 합니다. 큐잉 방식으로 구현하면 현재 작업이 끝난 후 차례로 처리되며, 구현이 간단하고 사용자도 에이전트
가 일하는 동안 다음 지시를 미리 입력해둘 수 있어 편리합니다. 반면 실시간 삽입 방식은 복잡성을 높이므
로, Ramp도 대기열(Queue) 방식을 򟻘했습니다 . 또한 API 레이어에는 세션 강제 중지 기능도 마련하
여, 사용자가 원할 경우 현재 진행 중인 작업을 중단시킬 수 있어야 합니다.
다중 사용자 협업 (Multiplayer): 설계 단계부터 한 세션에 여러 사용자가 참여할 수 있도록 고려합니다.

PR 생성 시 사용자의 권한으로 수행되며, 앞서 언급한 대로 PR 승인 절차를 어그러뜨리지 않습니다. Slack과
같이 별도 인증이 없는 플랫폼의 경우, 최초 사용 시 링크 클릭 등을 통해 GitHub 연동을 해두고, 이후 세션에서
는 Slack 사용자와 사내 계정(GitHub 계정)을 매핑하여 사용합니다.
Pull Request 생성 및 웹훅: 에이전트 작업이 완료되면 sandbox 내에서 브랜치를 푸시하고, API 레이어에서
GitHub API를 호출하여 PR을 생성합니다. PR 메타데이터(브랜치, 설명, 리뷰어 지정 등)는 에이전트가 작성
하거나 템플릿으로 자동 구성합니다. GitHub 웹훅을 설정하여 PR 상태 변화를 수신하고, 만약 PR이 머지되거
나 닫히면 해당 세션 DO에 이벤트를 보내 세션을 정리하거나 사용자에게 알림을 주도록 합니다. 또한 브랜치 푸
시 웹훅을 통해 에이전트 세션이 외부에서 (예: 사용자가 직접) 업데이트된 경우 이를 감지하여 세션 상태를 업
데이트할 수도 있습니다.
➡ 기술 스택: API 및 세션 레이어는  Cloudflare Workers + Durable Objects (TypeScript)로 구현합니다.
Cloudflare Workers 환경은 글로벌 엣지에서 낮은 지연으로 Slack/Web 등의 클라이언트 요청을 받아 에이전트 세션
과  통신하기에  적합합니다.  Durable  Object는  TypeScript  클래스  형태로  작성하고,  내부에서  SQLite (D1이나
Cloudflare Internal SQLite 등) 혹은 KV 스토어를 사용합니다. 실시간 통신은 WebSocket (Agents SDK)이나 SSE
방식으로 구현하고, 클라이언트 측 React 앱에서는 해당 스트림을 수신하여 출력 로그를 렌더링합니다. GitHub OAuth
연동 역시 Cloudflare Workers에서 처리 가능하며, Slack 명령 수신을 위한 엔드포인트도 Workers로 노출시켜 통합
할 수 있습니다 (또는 필요에 따라 Python 기반 Slack Bot 서버를 별도로 둘 수도 있지만, Workers로 통일 가능함).
4. 클라이언트 인터페이스 구현
에이전트의 가치를 극대화하려면, 사용자들이 편하게 접근할 수 있는 다양한 인터페이스를 제공해야 합니다. 이번 프로
젝트에서는 Slack 봇, 웹 대시보드/IDE, Chrome 브라우저 확장을 주요 클라이언트로 구현합니다.
Slack 챗봇: 회사 내 많은 사람이 사용하는 커뮤니케이션 도구인 Slack에 에이전트를 통합하면 자연스러운 바
이럴 효과를 얻을 수 있습니다. 사용자는 특정 채널에서 봇에게 자유형식 자연어로 말 걸 듯 요청을 보내면
됩니다 (예: "@AIAgent 주문 API에 버그가 있는지 확인하고 고쳐줘"). Slack 봇은 프롬프트 텍스트와 대화
스레드 맥락, 채널 정보를 이용해 어떤 리포지토리(프로젝트)를 다룰지 자동으로 분류합니다. 이를 위해 사
전에 각 리포지토리의 간단한 설명과 키워드를 준비하고, 소형 LLM 모델(예: GPT-3.5 Turbo 등의 빠른 모드)
을 사용하여 분류 작업을 수행합니다. 분류 결과가 애매하면 봇이 사용자에게 어느 저장소인지 재확인할 수도
있습니다. 일단 저장소가 결정되면, Slack 봇은 API 레이어에 해당 repo로 새로운 세션을 시작시키고 사용자
메시지를 전달합니다. 이후 에이전트의 작업 진행 상황을 중요한 단계마다 요약하여 Slack 메시지로 중계합니
다 (예: “코드 수정 중...”, “테스트 통과  - PR 생성 중...”). 이를 위해 에이전트에게 Slack 전용 출력 함수를 플
러그인으로 제공하거나, API 레이어에서 상태 변화를 받아 Slack 메시지를 보내는 식으로 구현합니다. 메시지
포맷은 Slack Block Kit을 활용하여, 예쁘게 꾸며진 카드 형태로 리포지토리 이름, 브랜치, 진행 상태, PR 링크
등을 표시합니다. 또한 사내 문화에 맞게 커스텀 이모지를 사용하면 봇을 더 친숙하게 만들 수 있습니다 (예: 진
행 중일 때 :loading: 아이콘, 완료 시 :shipit: 등을 표시).

투명하게 보여줍니다. 예를 들어, 일/주/월별 세션 생성 횟수, 에이전트가 만든 PR 수와 그 중 머지된 PR 비율
(이 지표가 에이전트 유용성의 핵심 척도입니다), 현재 실시간 사용 중인 세션 수(예: “현재 5명의 사용자가
프롬프트 입력 중” ) 등을 시각화합니다. 이러한 지표는 팀원들에게 동기를 부여하고, 관리자가 투자 대비

습니다. 사용자가 사내 웹앱을 사용하다가 UI 버그나 텍스트 오타 등을 발견하면, 확장 프로그램을 통해 해당 요

크롬 확장 사이드바(UI 패널)를 열어 에이전트 채팅 인터페이스를 제공합니다. 사용자가 현재 페이지에서
특정 부분을 선택(하이라이트)하면, 확장은 그 부분의 DOM 구조와 React 컴포넌트 정보를 추출합니다 .
(Ramp는 내부적으로 React 디버깅용 API를 사용했다고 하나, 공개 구현체로 React Developer Tools나 
ReactDOM의 직렬화, 또는 오픈소스 React Grab 등을 활용할 수 있습니다.)
그런 다음, 선택된 UI 정보와 사용자 입력을 조합해 에이전트 세션 요청을 생성합니다. 이때 스크린샷 이미지를
통째로 보내는 대신, 추출한 DOM/컴포넌트 정보만 전달하여 토큰 사용을 절약합니다. 에이전트는 해당 정
보를 바탕으로 어떤 컴포넌트 파일을 수정해야 할지 판단하고, 샌드박스에서 수정 작업을 수행합니다. 결과가
나오면 (예: "수정 완료 - PR 생성함"), 확장 프로그램은 사용자에게 성공 메시지와 PR 링크를 보여줍니다.
배포: 이 확장 프로그램은 회사 내부에서만 사용할 것이므로, 크롬 웹 스토어에 공개하지 않고 조직 정책으로 강

확장의 업데이트 URL을 등록하면, 직원들 브라우저에 자동으로 설치됩니다. 업데이트 서버는 간단한 JSON
manifest와 .crx 호스팅으로 구현 가능하며, Chrome 확장 자동 업데이트 프로토콜을 따르면 됩니다 (관련
가이드 문서 참고). 이렇게 하면 사용자는 별도 설치 과정 없이 브라우저 우측 상단에서 바로 에이전트 도구를
사용할 수 있습니다.

보안과 권한 관리: 내부 코드베이스에 대한 write 권한이 있는 에이전트이므로, 접근 제어가 중요합니다.
OAuth로 인증된 사내 직원만 사용 가능하도록 하고, 에이전트가 사용할 수 있는 리포지토리나 기능(예: 프로덕

검토 프로세스를 거치도록 합니다.
모델 선정과 비용: OpenCode를 통해 여러 LLM을 유연하게 쓸 수 있으므로, 회사 정책과 성능을 감안하여 모
델을 선택합니다. 예를 들어 코드 정확도는 GPT-4가 좋지만 비용이 높으므로, 간단한 요청은 3.5 Turbo로 처리
하고 중요한 생성은 GPT-4로 업스케일하는 전략을 취할 수 있습니다. 사내 프록시를 통해 OpenAI API 키를 관
리하거나, 혹은 self-hosted LLM을 연구해 볼 수도 있습니다.
모니터링 및 텔레메트리: 에이전트 자체의 로그와 이벤트도 모니터링 대상입니다. 세션 시작/종료, 에러 발생,
모델 응답 지연 등의 정보를 수집해 Sentry나 Datadog 등에 보내두면, 운영자가 성능 병목이나 오류를 파악하
고 개선할 수 있습니다. 또한 사용자의 피드백이나 에이전트 실수 사례를 모아서 지속적으로 프롬프트 튜닝이나
툴 업데이트에 반영해야 합니다.
기술 스택 요약: 요구사항에 비추어 최적의 기술 스택 조합은 다음과 같습니다:
Infra:Modal (빠른 VM 기동 및 스냅샷), Cloudflare Workers/DO (글로벌 저지연 API 및 세션 관리).
Core Agent:OpenCode (Go) – 서버 우선 아키텍처와 풍부한 플러그인 지원으로 최적.
Backend Integrations: Python 스크립트/툴 (테스트 실행, 브라우저 조작 등) – 범용성과 방대한 라이브러리
활용.
Frontend:React + TypeScript – 웹 대시보드와 크롬 확장 개발에 적합, 재사용성 높음.
Communication: Slack API + (Python or Node) – 사내 메신저 통합.
Data Storage: GitHub (코드), Cloudflare DO (세션 상태, 대화내용 SQLite), Optional 내부 DB (로그/통계).
프로젝트 단계별 진행:
인프라 세팅: Modal 이미지 제작 파이프라인 구성 및 Cloudflare DO 클래스 개발.
OpenCode 통합: 샌드박스에서 OpenCode 에이전트 실행 확인, 필요 플러그인 (git sync 대기 등) 개발.
API 개발: Durable Object를 통한 세션 관리 로직 및 WebSocket 스트림 구현.
클라이언트 개발: Slack 봇부터 시작해 웹 UI, Chrome 확장 순으로 구현. 각 단계에서 에이전트 API와 연동 테
스트.
통합 테스트: 샌드박스에서 PR 생성까지 시나리오 테스트, 여러 동시 세션과 멀티유저 시나리오 검증.
모니터링/통계: 운영상 필요한 대시보드와 알림 시스템 구축.
사내 홍보 및 교육: 기능 시연, 점진적 팀 온보딩을 통해 자연스러운 도입 유도 (Ramp 사례처럼 강제하지 않고
제품의 효용으로 사용자가 늘도록 유도).
이상으로 Ramp의 Inspect와 똑같은 서비스를 만들기 위한 상세 구현 방안을 살펴보았습니다. 이 아키텍처를 따르면,
모델 응답 속도 외에는 지연이 느껴지지 않을 만큼 빠르게 동작하면서도 사내 개발 워크플로우에 깊이 통합된 강력한 코
딩 에이전트를 구축할 수 있을 것입니다. 실제 Ramp도 해당 시스템 도입 후 짧은 시간 내에 전체 PR의 30% 이상을 에
이전트가 작성하게 되었고, 그 비율은 계속 증가하고 있다고 합니다. 여러분의 조직도 자체 도구를 소유함으로써 얻는
강점 – 자기 코드베이스와 환경에 최적화된 파워 – 을 누리게 되길 바랍니다.
